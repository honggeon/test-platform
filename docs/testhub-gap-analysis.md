## 三、差距详解

### 3.1 可视化流程编排（核心差距）

**TestHub 的实现：**

TestHub 提供真正的 DAG 画布式流程编排，用户可以：

- 从左侧组件面板**拖拽节点**到画布
- 在节点之间**拖拽连线**来表达执行顺序和数据依赖
- 点击节点在右侧属性面板配置参数
- 连线上可附加**条件表达式**实现分支逻辑（if/else）
- 运行时节点颜色实时变化（灰/蓝/绿/红 对应 未执行/执行中/通过/失败）
- 9 种内置节点类型：HTTP、SQL、check、checkobj、sleep、convert、const、sql_begin、sql_commit

```
┌──────────────────────────────────────────────────────┐
│  组件面板 (左)         画布区域 (中)      属性面板 (右) │
│ ┌──────────────┐   ┌─────────────────┐  ┌──────────┐│
│ │ 🔲 HTTP 请求  │   │                 │  │ 步骤名称  ││
│ │ 🗄️ SQL 查询   │   │  [开始]         │  │ 请求方法  ││
│ │ ✅ 数据校验   │   │    │            │  │ URL      ││
│ │ 🔄 数据转换   │   │    ▼            │  │ 请求参数  ││
│ │ ⏱️ 等待延时   │   │  [HTTP请求]──┐  │  │ 断言配置  ││
│ │ 📦 常量定义   │   │    │         │  │  │ 数据提取  ││
│ │ 📊 对象对比   │   │    ▼         ▼  │  │ ...      ││
│ │ 💾 事务管理   │   │  [校验]   [SQL] │  │  │          ││
│ └──────────────┘   │    │        │   │  └──────────┘│
│                    │    ▼        ▼   │              │
│    拖入节点即可     │  [结束]         │              │
│                    └─────────────────┘              │
└──────────────────────────────────────────────────────┘
```

**当前项目的实现：**

当前项目的 `scenario-orchestration-view.tsx` 是**垂直列表式卡片**编排：

- 使用 `@dnd-kit` 实现步骤列表的拖拽排序
- 步骤间的数据依赖通过**表单选择器**配置（选择"源步骤"和 JSONPath）
- 每个步骤通过弹窗表单创建，包含 7 个折叠配置区
- 没有可视化连线来表达依赖关系

**补齐方案：**

采用 **ReactFlow** (reactflow.dev) 替换当前的 `@dnd-kit` 列表方案：

1. 步骤映射为 ReactFlow 的 `nodes`，数据依赖映射为 `edges`
2. 自定义每种步骤类型的节点渲染组件（HTTP/SQL/校验等用不同颜色和图标）
3. 连线映射为数据依赖——从节点 A 的输出端口连线到节点 B 的输入端口时自动创建 `StepDataMapping`
4. 支持画布内的 inline 编辑（双击节点展开配置面板）
5. 新增节点类型定义（见 3.3）

### 3.2 插件式架构（核心差距）

**TestHub 的实现：**

```java
// TestHub 的组件接口（简化）
public interface Component {
    String getType();           // 组件类型标识
    String getName();           // 组件显示名称
    ComponentResult execute(ComponentContext ctx);  // 执行逻辑
    List<Parameter> getParameters();  // 可配置参数
}

// 通过 Spring 自动发现和注册所有 Component 实现类
// 新增一种组件只需：实现接口 + @Component 注解 + 添加到前端组件面板
```

所有操作（HTTP、SQL、校验、转换等）都是独立组件，遵循统一接口，可以通过插件热加载扩展。

**当前项目的实现：**

- 场景步骤目前**仅支持 HTTP 请求**
- 步骤类型硬编码在 `ScenarioStep` 模型中，没有抽象出组件接口
- 新增步骤类型需要修改模型层、执行引擎、前端表单等多个位置

**补齐方案：**

1. 定义 `StepPlugin` 抽象基类，包含 `type`、`name`、`validate_config()`、`execute(context)` 等接口
2. 将现有 HTTP 执行逻辑抽离为 `HttpStepPlugin`
3. 新增 SQL、Check、Sleep 等插件
4. 通过 Python 的 `entry_points` 或自定义注册机制实现插件发现
5. 前端通过插件元数据动态渲染节点配置表单

### 3.3 内置步骤类型不足

**TestHub 内置 9 种组件：**

| 组件 | 功能 | 当前项目对应 |
|------|------|------------|
| `http` | HTTP 请求 | ✅ 已支持 |
| `sql` | 执行 SQL 语句 | ❌ 缺失 |
| `sql_begin` | 开启数据库事务 | ❌ 缺失 |
| `sql_commit` | 提交数据库事务 | ❌ 缺失 |
| `check` | 数据校验（断言） | ✅ 步骤断言 |
| `checkobj` | 对象/列表结构对比 | ❌ 缺失 |
| `sleep` | 延时等待 | ✅ delay_ms |
| `convert` | 数据格式转换 | ✅ transform_expression |
| `const` | 常量定义 | ✅ 场景全局变量 |

**需补齐的步骤类型：**

1. **SQL 执行步骤** — 连接数据库执行查询/更新，将结果写入上下文供后续步骤使用
2. **数据库事务步骤** — `begin` / `commit` / `rollback`，多步骤包裹在事务中
3. **条件分支步骤** — 根据表达式结果选择不同的执行分支（不仅仅是 continue_on_failure）
4. **循环步骤** — 对数组数据逐条执行子步骤
5. **脚本步骤** — 执行自定义 Python/JavaScript 脚本进行复杂数据处理
6. **等待步骤** — 轮询等待某个条件满足（如异步任务完成）

### 3.4 规则引擎（重要差距）

**TestHub — NsRule 规则引擎：**

NsRule 是 TestHub 自研的轻量级规则引擎，类似 Java 生态的 Drools 但更轻量：

- 节点执行的前置条件判断
- 连线上的条件路由（if/else 分支）
- 数据转换规则
- 断言规则
- 支持 `if-then-else`、`switch-case`、`loop` 等控制流
- 规则可以 DSL 文本形式编写，也可以在画布上可视化配置

**当前项目：**

- 仅支持简单的 `condition_expression` 字段（字符串表达式）
- 没有独立的规则引擎，条件判断散落在执行引擎各处
- 不支持分支执行路径

**补齐方案：**

1. 在步骤模型中增加 `condition_type` 字段（expression / rule_engine / script）
2. 集成轻量级规则引擎，如 Python 的 `business-rules` 或自研基于 JSON 的规则定义
3. 规则定义示例：
```json
{
  "conditions": {
    "all": [
      { "fact": "previous_status", "operator": "equal", "value": 200 },
      { "fact": "response.code", "operator": "equal", "value": 0 }
    ]
  },
  "actions": [
    { "type": "execute_step", "step_id": "next_success" }
  ],
  "else_actions": [
    { "type": "execute_step", "step_id": "next_failure" }
  ]
}
```

### 3.5 百宝箱开发工具集（重要差距）

TestHub 内嵌了离线开发工具箱，覆盖日常开发和测试中常用的工具：

| 类别 | 工具 | 优先级 |
|------|------|--------|
| 格式类 | JSON/XML/SQL/CSS 格式化 | P1 |
| 编解码 | Base64、MD5、AES 加解密 | P1 |
| 编解码 | JWT 解析/调试、URL 编解码 | P1 |
| 开发类 | 正则表达式测试 | P1 |
| 开发类 | 时间戳转换、CRON 表达式工具 | P2 |
| 文件类 | 文本对比（diff）、文件内容检索 | P2 |
| 生成类 | 二维码生成、色值转换 | P3 |

当前项目**完全没有这类辅助工具**。

**补齐方案：**
- 这些工具多数可以用纯前端库实现，无需后端支持
- 在 `ui/components/` 下创建 `toolbox/` 模块
- P1 工具建议优先实现，可就近集成到 API 测试 / 场景测试界面中（如 JSONPath 测试器嵌入到数据提取配置旁边）

### 3.6 权限控制体系（重要差距）

| 维度 | TestHub | 当前项目 |
|------|---------|---------|
| 认证框架 | sa-token（成熟） | JWT + bcrypt（基础） |
| 权限模型 | RBAC（角色-行为） | 无细粒度权限 |
| 权限级别 | 系统级 + 项目级 | 无区分 |
| 权限粒度 | 行为级别（增删改查） | 无 |
| 管理界面 | 内置权限管理 UI | 无 |

**需补齐：**
1. 定义角色模型（admin / project_owner / editor / viewer）
2. 实现资源级权限检查（项目、文件夹、测试用例的 CRUD 隔离）
3. 后端中间件拦截 + 前端路由守卫

---

### 3.7 桌面应用（可选差距）

TestHub 通过 **electron-egg**（Electron + Java 后端嵌入式运行）提供桌面应用，支持离线使用。

当前项目仅有 Web 端。如果目标用户场景包含内网隔离环境（云桌面等），可考虑后续用 **Tauri**（更轻量）或 Electron 打包。

## 五、我方核心优势（不可丢失）

补齐差距的同时，以下能力是当前项目对 TestHub 的**压倒性优势**，需持续投入：

| 能力 | 说明 |
|------|------|
| **AI 智能测试生成** | LangGraph + DeepSeek 自动生成测试计划/用例/脚本，TestHub 完全不具备 |
| **AI 智能诊断** | 失败自动分析 + 知识图谱定位代码 + 修复建议，测试领域的技术壁垒 |
| **代码知识图谱** | tree-sitter 静态分析，链接测试失败到源代码，TestHub 无法实现 |
| **自然语言交互** | 通过聊天界面操作测试全流程，降低使用门槛 |
| **多语言国际化** | 中/英/日三语，TestHub 仅中文 |
| **HAT 框架** | YAML/Excel 关键字驱动测试 + pytest + Allure，适合传统测试团队 |

## 六、执行引擎对比

| 维度 | TestHub | 当前项目 |
|------|---------|---------|
| 执行模式 | DAG 拓扑排序 + 无依赖并行 | 顺序 for 循环 |
